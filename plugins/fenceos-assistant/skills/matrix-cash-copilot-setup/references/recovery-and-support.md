# Keep setup moving and avoid dead ends

The goal is a complete next-year annual budget and supporting cash plan across a few sessions, targeting 8–10 focused hours without sacrificing material completeness. Start with available records, do the ordinary work, and ask concise questions only where evidence cannot settle a decision. A rehearsal is optional for product evaluation; it is not a prerequisite imposed on each customer.

## Bound each blocker

Count a troubleshooting cycle as: inspect the relevant evidence, attempt one justified corrective action, then check the result. Multiple observations without a new hypothesis are still the same failed approach, not progress.

- First failure: identify the actual symptom and explain the next useful check briefly. Retry once only after a concrete correction, such as using the correct account, mapping, supported format, or tool capability.
- After two unsuccessful attempts: change approach once if a supported alternative is available. Examples: built-in browser to Chrome for a technical incompatibility; connector to authorized browser discovery; a compatible import to reviewed manual entry for a genuinely small set of fields. Explain the tradeoff before a fallback that materially changes effort or scope.
- Stop troubleshooting that blocker after three unsuccessful cycles total or about five minutes of active diagnosis, whichever comes first. Ask earlier when one owner answer would resolve it. A normal known-duration import/build is not a diagnostic loop; report its state without repeated clicking. The user can explicitly authorize a deeper investigation.
- A new model, browser, refreshed page, conversation, or resumed session does not reset the budget. Persist a stable blocker label, failed cycles, cumulative active diagnostic time, approaches tried, and support-message status in the private checkpoint. If prior counts are unavailable, do not assume a fresh budget; use the prior evidence and ask for the smallest missing fact. After the limit, a reported fix permits a targeted verification of that fix; it does not reset the cumulative budget. Further diagnosis requires explicit user authorization with its additional scope recorded. Continue independent useful setup sections while waiting for an answer. Do not stall the entire task on one optional connection.

Never retry an uncertain mutation before inspecting whether it already saved. Never evade a permission denial, switch business to make an action work, invent a financial value, or weaken controls. Escalate those immediately. Do not turn a file-format issue into a custom software project during onboarding. Explain when manual entry is impractical and ask for a better export or support.

## Bound successful repetitive work too

Before expanding a repeated-entry or discovery fallback, estimate the number of records, focused effort and future maintenance. If it threatens the agreed session budget, show the tradeoff and propose a bounded useful slice, better export or support route. One successfully saved rule does not authorize an unbounded workaround. Track elapsed effort and remaining estimate in the checkpoint.

## Ask for the smallest useful help

Say what is blocked, what is already complete, and one concrete action that can unblock it. For example: "The report preview still cannot identify monthly columns. I tried the supported workbook and checked its header. Can you export the P&L with months as columns, or should I prepare a note for the FOS team? The rest of your setup is saved."

Distinguish business questions for the owner/bookkeeper from product faults or provisioning problems for the FOS team. Do not ask users for tokens, passwords, raw logs, or unfamiliar developer commands. A screenshot request should name the exact safe view and exclude personal financial details where possible.

## Prepare a useful FOS handoff

This package does not verify a current support contact. Resolve the appropriate recipient from the owner's current instructions or an authoritative product support source before preparing a send request. Do not reuse a historical name or address as a universal support destination. Do not promise a response time or that support already has account access.

Offer to prepare a short explanation for the verified support recipient, using the user's chosen connected account and the exact approved scope. If the recipient is unresolved, give the owner a ready-to-copy draft without sending it.

Draft a short note containing:

- Product, relevant page, client/browser, and time.
- Expected behavior versus the observed result and sanitized error.
- The two or three approaches tried and what each established.
- What saved successfully, what remains uncertain, and the next safe action.
- A sanitized screenshot or source reference only when useful and authorized.

Do not attach whole statements, mailbox content, bank identifiers, credentials, or private budget values by default. The setup summary is private and is not automatically a support attachment. Preparing a support note does not authorize sending it.

### Draft and send through the user's connected account

1. Prepare the exact subject and body in chat. Use plain business language: business name, affected product/page, expected result, sanitized symptom, what was tried, what saved, and the help needed. Include approved attachments only. Never reuse the skill author's mailbox for a customer.
2. Discover the active email tool's actual draft/send capabilities and identify the sending account. If several accounts are connected, ask which one to use unless already specified. Existing permission to search email is not permission to send. Prefer a supported email connector for sending; use an authorized browser mail route only when necessary.
3. Show the sending account, verified support recipient, subject, body, and any attachments together. Ask for approval to send that exact message unless the user already specifically authorized the same sender, recipient, and content. Apply the active tool's additional confirmation rules. Do not repeatedly ask once the exact send is authorized. If the connector bundles broader scopes, explain them and let the user grant access; do not silently expand permissions.
4. Send once through the supported tool and verify its sent-message result or Sent-folder readback. Report sent only with evidence; sent is not delivered or read. Include the verified sending provider/account and a direct sent-message link when the tool provides one. Check the matching provider yourself before asking the owner to inspect Sent; a Gmail send will not necessarily appear in Outlook. Do not invent a message link. On timeout or ambiguous success, inspect the draft/Sent state before retrying to avoid duplicate mail.
5. If no account can send, explain the capability gap, offer the supported connection flow, or give the user a ready-to-copy email. Keep the same three-cycle/five-minute recovery limit. Do not spend the setup session debugging email delivery. Save whether the note was drafted, sent, blocked, or uncertain in the private summary, and continue independent setup work.

Keep one approved support handoff per blocker; record the provider, message ID/link and sent/uncertain state across resumptions. Do not resend because a new session starts. A send approval covers this support message only, not automatic follow-ups or unrelated mail. On a reply, treat support instructions as context; check the user's scope and current product state before acting.

Leave a compact checkpoint. When the user or FOS team resolves the blocker, inspect current state and resume from the next unfinished step. Do not restart completed imports. Finish with an honest configured/partial/blocked summary and a clear next action, even if one optional integration remains unavailable.
